# 架构与重构决策

## 核心取舍

InvestLab面向低频的QQQ/TQQQ投资监控：本地保存账户，按完整交易日计算，保留可回放证据。架构以Python应用、SQLite账本和只读网页为核心；在保留已回归验证的数值模块之外，建立明确的数据入口、运行编排与复核接口。

| 层 | 职责 | 实现 |
|---|---|---|
| 数据入口 | 请求、原文证据、完整交易日、价格校验 | `providers.py`，兼容引擎的来源冲突门禁 |
| 事实账本 | 已确认流水与估值，历史报告、证据、状态 | 同一个SQLite数据库；`ledger.py`、`core.py` |
| 数值引擎 | 指标、分步配置、研究模型、情景 | `engine/`；独立子进程，不污染应用导入路径 |
| 独立复核 | 解析费用算法、净值重放、前缀因果检验 | `verification.py` |
| 运行编排 | 单写者锁、状态、回读、备份、短摘要 | `service.py`、`storage.py` |
| 展示 | 今日判断、仓位差距、研究比较、历史记录 | `server.py`、`web/`；本机只读 |

## 为什么不是全量重写

原模型已包含复权历史、输入哈希、成熟模型与概率研究。把这些全部重写容易引入无法解释的数值差异。先用同一份数据比较重构前后结果，再为新模块增加独立检查。v6不改变既有60/40目标、分步规则和研究参数。

旧代码从源码目录读写data；v6将数据改到`INVESTLAB_HOME/data`，源码与冻结配置随Python包安装。历史源码包和数据快照留在私有迁移目录；新版本的源代码身份跟随每次报告保存。

## 四类不同事实

- 目标：长期希望60/40。
- 建议：本轮从最后确认仓位出发的一步。
- 估值：某日用户明确确认的各资产人民币价值。
- 流水：券商已确认的入金、买卖、费用等。

建议无法写入流水表。流水导入必须`confirmed=true`、带稳定ID和时区时间；同ID不同内容失败，整批回滚。流水表和估值表禁止UPDATE/DELETE。导入错误通过新建VOID纠正流水，引用原ID并说明原因，原始记录仍保留。重复作废、引用另一账户或币种、作废纠正本身均拒绝。作废后完整重放，如果导致后续卖出超仓或现金为负，整批拒绝，需先核对相关流水链。

## 收益与币种

流水按账户、币种独立重放。已知买入成本时计算加权平均成本及已实现损益；只有期初股数时成本未知，不编造。此计算不是报税成本核算。

旧账户仅有聚合估值，不提供完整资金流与份额，无法据此算时间加权收益或内部收益率；v6明确保留未知。没有同日确认汇率，不把USD、HKD和CNY加总。新流水不会自动覆盖旧聚合估值：需要导入明确的完整新估值才推进默认监控账户。

## 运行一致性

每个写操作获得同一OS锁。报告先由引擎计算、存入原表；应用按run_id从DB原样取回复核，再写新应用记录。完整数据备份经manifest和SQLite校验通过后，operation才变为SUCCEEDED。

文件最新指针只是派生物；看板从DB查最新记录及operation状态。失败或中断的部分结果会被标明；最新尝试失败时，历史成功报告不能遮蔽故障。行情是否过期按最新完整交易日判断，观察天数按源码版本分别统计。通知有稳定去重ID，默认只保存在本地；没有发送回执就不声称已送达。ChatGPT定时任务仍作为原来的通知通道，systemd作为可选替代，不同时安装两套调度。
